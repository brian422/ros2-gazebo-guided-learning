# Demonstration storyboard — 60 to 90 seconds

## Goal

Show one coherent engineering result: a ROS 2 rover follows a fixed inspection
route in simulation, responds to a mathematical hazard threshold, records its
mission, and has focused tests. Keep the language technical and factual.

## Preparation

Before recording:

1. complete the validation matrix;
2. restore the default `hazard_threshold: 6.00`;
3. build, source, and run the tests;
4. arrange VS Code, Terminal, Gazebo, and RViz windows;
5. enlarge terminal fonts and hide personal paths or notifications;
6. rehearse once and verify the expected retreat occurs;
7. have the newest CSV and test summary ready in separate terminals.

Do not wait for package installation or a full build during the final video.
The launch command itself should be shown live.

## Storyboard and suggested narration

| Time | Visual | Suggested factual narration |
|---:|---|---|
| 0–7 s | VS Code Explorer showing five packages and `docs/`. | “This project is a five-package ROS 2 Humble workspace for an educational hazardous-area inspection simulation.” |
| 7–14 s | Terminal enters the single main launch command. | “One bringup launch composes Gazebo Harmonic, the robot model and bridges, hazard sensing, mission control, services, logging, and RViz.” |
| 14–23 s | Gazebo world and spawned rover; briefly show start area, barriers, passage, stations, and marked zone. | “The lightweight world uses primitive geometry. The differential-drive rover publishes simulated odometry, wheel states, and lidar data.” |
| 23–31 s | RViz RobotModel, TF, scan, cyan route, and status text. | “RViz displays the robot and frame tree, laser scan, fixed route, and current mission status.” |
| 31–38 s | Service call `/mission/start`; state terminal begins changing. | “A standard Trigger service starts an explicit finite-state mission.” |
| 38–51 s | Accelerated or carefully cut footage of station 1 inspection and passage transit. | “A proportional controller uses odometry to rotate, move toward known waypoints, limit velocity, and stop for inspection.” |
| 51–64 s | Hazard level rises; status changes through hazard and retreat. | “Near the configured hazard source, the threshold interrupts normal motion. The controller publishes zero, then returns to the previous safe route point.” |
| 64–71 s | State reaches `ABORTED` after retreat. | “After retreat the mission remains aborted until an operator reset, making the outcome explicit.” |
| 71–79 s | Terminal shows CSV header and representative final rows. | “The logger records pose, command, hazard, and state in a timestamped CSV for review.” |
| 79–87 s | Terminal shows `colcon test-result --verbose`. | “Pure unit tests check the hazard model, waypoint mathematics, angle wrapping, speed saturation, invalid inputs, and state transitions.” |
| 87–90 s | README limitation statement. | “This is a known-route system-integration exercise, not SLAM, obstacle avoidance, or field-ready safety software.” |

Target length: **80–90 seconds**. If limited to 60 seconds, shorten the world
overview and waypoint footage; keep the hazard response, CSV, tests, and scope
statement.

## Commands to stage

Main launch:

```bash
ros2 launch hazard_inspection_bringup inspection_demo.launch.py
```

Mission start:

```bash
ros2 service call /mission/start std_srvs/srv/Trigger "{}"
```

State and hazard observation:

```bash
ros2 topic echo /mission/state
ros2 topic echo /hazard/level
```

Test result:

```bash
colcon test-result --verbose
```

CSV excerpt:

```bash
head -n 3 ~/.ros/hazard_inspection_rover/logs/mission_<timestamp>.csv
tail -n 5 ~/.ros/hazard_inspection_rover/logs/mission_<timestamp>.csv
```

Replace `<timestamp>` with the real file name before recording.

## Required screenshots

Capture high-resolution images for the README or repository evidence:

1. repository tree with all five packages;
2. Gazebo world showing the rover, starting area, passage, stations, and hazard
   marking;
3. RViz integrated view showing RobotModel, TF, laser scan, route, and status;
4. terminal showing the hazard-related state sequence;
5. CSV header and representative mission rows;
6. zero-failure test summary;
7. optional TF frame graph generated by `view_frames`.

Crop only empty desktop area. Do not crop away command names, topic names, or
the evidence being discussed. Remove personal email, usernames, and unrelated
notifications.

## Editing guidance

- Real-time waiting may be shortened with a cut or speed-up, but do not edit
  the state order or imply a faster controller response than observed.
- Keep the terminal and simulation readable; 1080p is preferable.
- Use captions for `/hazard/level`, `/mission/state`, and `/cmd_vel` if the
  terminal text is small.
- Do not add dramatic claims, emergency imagery, or hardware footage that is
  not part of the project.
- Link the hosted video from the README instead of committing a large binary.

## Questions the video should answer visually

- Can the reviewer identify the package architecture?
- Does one command start the full system?
- Are sensing, frames, and status visible?
- Does the robot move along the declared known route?
- Is the hazard response distinguishable from normal completion?
- Is a data record created?
- Were deterministic behaviors tested?
- Are limitations stated?

## Final narration check

Every sentence should be something you personally verified and can explain.
Avoid “autonomous,” “intelligent,” “safe,” or “robust” unless immediately
qualified by the exact test and limited simulation context. Preferred phrases
are “predefined route,” “educational proportional controller,” “simulated
hazard threshold,” and “tested behavior in this Gazebo world.”
